# Посібник користувача NectarinePanel

[English](../en/user-guide.md) · **Українська** · [Русский](../ru/user-guide.md) ·
[Polski](../pl/user-guide.md)

Цей посібник призначений для тих, хто розгортає проєкти та керує ними через
вебінтерфейс. Встановлення сервера й зміна вихідного коду описані в
[посібнику розробника](developer-guide.md).

> NectarinePanel керує привілейованими операціями на одному VPS. Зберігайте
> резервну копію поза сервером, перевіряйте відновлення та надавайте кожному
> користувачеві лише необхідний доступ.

## Встановлення

Встановлюйте панель на окремий VPS з Ubuntu 24.04 LTS, доменом із A/AAAA
записом на VPS, щонайменше 2 GB RAM, 20 GB вільного місця та доступом root або
sudo. Клонуйте перевірений тег релізу і запустіть інсталятор від root:

```bash
git clone --branch vX.Y.Z --depth 1 https://github.com/JanekDeveloper/NectarinePanel.git
cd NectarinePanel
sudo ./installer/install.sh --domain panel.example.com --email admin@example.com
```

| Параметр | Призначення |
| --- | --- |
| `--domain`, `--email` | Публічний домен панелі та email для Let's Encrypt. |
| `--admin-user`, `--admin-password` | Логін і пароль першого власника. Пароль краще вводити інтерактивно або брати із захищеного сховища. |
| `--storage-root` | Шлях до постійного сховища панелі та проєктів. |
| `--telegram-token`, `--telegram-owner-id` | Необов’язкові токен Telegram-бота та ID чату власника. |
| `--public-ip` | Публічний IP VPS, якщо автовизначення не підходить. |
| `--source` | Довірена локальна копія вихідного коду замість клонування. |
| `--repository`, `--ref` | URL репозиторію та закріплений Git-тег/ref для встановлення. |
| `--max-upload-mb` | Максимальний розмір завантажуваних файлів у MB. |
| `--backend-port`, `--frontend-port`, `--agent-port`, `--adminer-port` | Перевизначення зайнятих loopback-портів. |
| `--non-interactive` | Не ставити запитань, а завершуватися за відсутності обов’язкових значень. |
| `--skip-ssl` | Не випускати сертифікат; використовуйте лише за зовнішнього завершення TLS. |
| `--dry-run` | Перевірити план встановлення без зміни VPS. |

Інсталятор налаштує служби, Nginx, TLS, PostgreSQL, Valkey і System Agent. Якщо
не передано `--admin-password`, початковий пароль власника буде показано один
раз; збережіть його в менеджері паролів. Відкрийте `https://panel.example.com`,
увійдіть, змініть тимчасові дані та перевірте
`systemctl status vps-panel-backend vps-panel-worker vps-panel-frontend`.

Використовуйте лише закріплений тег релізу, а не неперевірену рухому гілку.
Порядок оновлення є в [Оновлення панелі](#оновлення-панелі), параметри
інсталятора — у [документації зі встановлення](installation.md).

## 1. Вхід і вибір мови

Відкрийте адресу панелі та увійдіть за обліковим записом, створеним
інсталятором або власником. Мову можна змінити на сторінці входу або в бічному
меню. Доступні українська, англійська, російська та польська. Вибір зберігається
у браузері й файлі cookie.

Якщо налаштовано вхід через Telegram, почніть вхід у панелі, відкрийте бота за
показаним посиланням і підтвердьте короткочасний запит. Поверніться до тієї самої
вкладки браузера — сесія завершиться автоматично. Не підтверджуйте запит, якого
ви не створювали.

## 2. Ролі та доступ

| Роль | Доступ |
| --- | --- |
| `owner` | Повний доступ, користувачі, безпека та всі проєкти. |
| `admin` | Усі проєкти й операційні дії, крім керування власником і безпекою. |
| `maintainer` | Лише призначені проєкти: розгортання, середовище виконання, файли та редагування змінних. Без перегляду секретів і видалення проєкту. |
| `viewer` | Читання призначених проєктів, логів, файлів і замаскованих змінних. |

Членство в проєктах застосовується до ролей `maintainer` і `viewer`. Прихована
кнопка не є захистом: серверна частина перевіряє кожну операцію.

## 3. Створення проєкту

Відкрийте **Проєкти → Новий проєкт**. Найпростіше почати із шаблону;
користувацький проєкт дає змогу налаштувати всі параметри середовища виконання.

### Вибір джерела

- **Git-репозиторій**: укажіть HTTPS-адресу й гілку. Кожне розгортання клонує
  новий незмінний реліз. Можна розгорнути конкретну гілку, тег або коміт.
- **Файли / ZIP**: створіть проєкт без репозиторію, потім завантажте `.zip` у
  вкладці **Деплої**. Архіви з небезпечними шляхами, посиланнями або надмірним
  розміром після розпакування відхиляються.

Для приватного репозиторію GitHub налаштуйте в параметрах проєкту один із
варіантів:

1. **Fine-grained token**: створіть на GitHub токен з обмеженим доступом лише до
   потрібного репозиторію та дозволом **Contents: Read-only**. Збережіть його в
   NectarinePanel як облікові дані типу «токен». Використовуйте звичайну
   HTTPS-адресу й не вставляйте токен у неї.
2. **Deploy key**: створіть окрему пару ключів SSH, додайте відкритий ключ у
   розділі GitHub **Repository → Settings → Deploy keys** без права запису, а
   закритий ключ збережіть у NectarinePanel як ключ розгортання. Використовуйте
   SSH-адресу репозиторію.

Облікові дані зберігаються зашифрованими й не потрапляють у параметри задач
розгортання. Якщо доступ до репозиторію змінюється, одразу видаліть або замініть
ключ.

### Вибір середовища виконання

| Середовище виконання | Для чого | Важлива поведінка |
| --- | --- | --- |
| Контейнер Docker | Більшість API, ботів і вебзастосунків | Збирає `Dockerfile` репозиторію; забезпечує ізоляцію та застосування обмежень ресурсів. |
| Docker Compose | Застосунки з кількох контейнерів | Запускає файл Compose; політика ресурсів використовується лише для моніторингу. |
| Статичний Nginx | Зібрані статичні сайти | Публікує зазначений вихідний каталог без процесу застосунку. |
| systemd | Застосунки, що запускаються безпосередньо на сервері | Запускає команду старту від окремого непривілейованого користувача. |
| PM2 | Застосунки Node.js під керуванням PM2 | PM2 працює всередині обмеженого системного модуля проєкту. |
| Minecraft Forge | Forge-сервер | Окремі налаштування, консоль, файли й резервне копіювання. |

Зміна команди запуску в панелі не переписує `Dockerfile` з репозиторію. Для
Docker команду контейнера визначають `CMD` і `ENTRYPOINT` у Dockerfile. Змініть
їх або використовуйте налаштовуваний сценарій запуску. Команда запуску з панелі
застосовується до середовищ, що працюють безпосередньо на сервері, і під час
початкової генерації шаблону.

### Перевірка перед першим розгортанням

- гілка існує, а облікові дані дають доступ на читання;
- команди збірки й запуску відповідають вибраному середовищу;
- усередині Docker застосунок слухає `0.0.0.0`, а не лише `127.0.0.1`;
- порт проксі збігається з портом застосунку;
- секрети розміщені у **Змінних**, а не в Git;
- постійні дані змонтовані з `shared/`;
- HTTP-перевірка працездатності повертає код 2xx або 3xx.

## 4. Розгортання й відкат

Відкрийте проєкт і вкладку **Деплої**.

- Розгортання з Git може приймати конкретну ревізію. Порожнє значення
  використовує налаштовану гілку.
- Розгортання з ZIP приймає лише `.zip` і призначене для проєктів без репозиторію.
- Активна задача показує стан і перебіг виконання.
- Історія релізів містить ревізію, час, шлях, результат і збережений лог.

Успішне розгортання створює реліз у
`projects/{project_id}/releases/{release_id}` й атомарно спрямовує `current` на
нього. Невдалий реліз не замінює активний.

Для відкату виберіть успішний реліз, підтвердьте його ім'я або ревізію й
запустіть операцію. Відкат активує реліз, але не відновлює бази даних і
постійні файли з `shared/`. За потреби відновіть їх із відповідної резервної
копії.

Якщо задача завершилася помилкою, відкрийте лог і виправте першу значущу
причину. Повторне розгортання без зміни джерела або конфігурації зазвичай матиме той
самий результат.

## 5. Керування запущеним проєктом

В огляді показано стан і доступні метрики. Кнопки відповідають фактичному стану:
**Запустити** відображається для зупиненого проєкту, **Зупинити** й
**Перезапустити** — для запущеного.

- **Логи** показують журнали середовища виконання й, коли можливо, оновлюються
  наживо.
- **Консоль** надсилає команди в середовище виконання проєкту й не є оболонкою
  з правами суперкористувача. Docker
  виконує команди в контейнері проєкту, Minecraft використовує RCON, а systemd,
  PM2 і Compose надають обмежені операції.
- **Cron** виконує команди через ту саму захищену межу середовища виконання.
  Статичні проєкти не підтримують завдання cron.

Повідомлення `no job control in this shell` означає, що інтерактивну оболонку
запущено без справжнього TTY. Звичайні команди працюють, але `Ctrl+Z`, `fg` і
`bg` недоступні. У вебконсолі використовуйте неінтерактивні команди.

## 6. Змінні та секрети

Вкладка **Змінні** — джерело змінних оточення для середовища виконання.

- Паролі, токени й інші облікові дані позначайте як секретні.
- Секретні значення шифруються та маскуються у списку.
- **Показати** вимагає введення точного ключа. Дія потрапляє в аудит без
  відкритого значення.
- **Історія** зберігає версії. Відкат створює нову версію й не стирає історію.
- Імпорт `.env` читає буквальні записи `KEY=value` і не підставляє змінні
  оболонки. Режим **Об'єднати** оновлює передані ключі, а **Замінити** видаляє
  ключі, яких немає в імпортованому файлі.

Зміна змінних не запускає розгортання автоматично. Перезапустіть або повторно
розгорніть проєкт. Показаний секрет вважайте розкритим: не вставляйте його в
логи, знімки екрана, систему задач або чат.

## 7. Безпечна робота з файлами

Корінь проєкту містить:

```text
releases/   незмінні релізи
current     символічне посилання на активний реліз
shared/     постійні файли між розгортаннями
```

Для переходу натисніть папку або сегмент шляху. Підтримувані масові операції
працюють із кількома вибраними елементами. Обчислення розміру великої папки може
тривати довше.

`current` — символічне посилання, а не звичайна папка. Панель безпечно розв'язує
посилання всередині кореня проєкту. Якщо застосунок записує дані всередину
контейнера без прив'язки каталогу з `shared/`, цих файлів не буде у файловому
менеджері й вони можуть зникнути після заміни контейнера. SQLite, завантажені
файли та інший стан зберігайте, наприклад, у змонтованій папці `shared/data`.

Перед видаленням або переміщенням зупиніть застосунок, який може записувати у
файли. Перед масовими незворотними змінами створюйте резервну копію.

## 8. Домени й TLS

Перед додаванням домену створіть DNS A/AAAA запис на адресу VPS і дочекайтеся
його публічного розв'язання. У вкладці **Домени**:

1. додайте ім'я хоста й перевірте порт проксі;
2. перевірте створений HTTP-маршрут;
3. випустіть сертифікат Let's Encrypt;
4. перевірте HTTPS і перевірку працездатності застосунку.

Не запускайте примусовий випуск багато разів під час помилок DNS або
маршрутизації: Let's Encrypt обмежує частоту запитів. Оновлення виконується за
розкладом, а строк дії та відбиток сертифіката зберігаються панеллю.

## 9. Бази даних

Сервер бази даних і база проєкту — різні сутності. Спочатку додайте облікові
дані сервера, потім створіть або під'єднайте базу. Підтримуються PostgreSQL,
MySQL/MariaDB, SQLite й Redis/Valkey із можливостями конкретної СУБД.

- Рядок підключення можна додати до змінної проєкту.
- Створення дампа, відновлення й видалення виконуються як фонові задачі.
- Для відновлення потрібен сумісний дамп і підтвердження.
- Перед відновленням або видаленням SQLite зупиніть проєкт.
- Redis/Valkey показує підключення й стан, але не імітує реляційні таблиці або
  відсутню ізоляцію.

Перед незворотною міграцією створюйте свіжий дамп і перевіряйте застосунок після
відновлення.

## 10. Резервні копії та відновлення

Автоматичне резервне копіювання вимкнене, доки не налаштована політика. До копії
проєкту можна включити оточення, активний реліз, спільні дані, завантажені файли,
логи, дампи баз даних і дані Minecraft. Повна копія панелі може містити базу
панелі, конфігурацію, вузли Nginx, проєкти та стан планувальника.

Кожен архів має маніфест і контрольну суму SHA-256. Стан «успішно» доводить
створення архіву, але не можливість відновлення. Для робочого середовища:

1. налаштуйте розклад і строк зберігання;
2. копіюйте критичні архіви за межі VPS;
3. перевіряйте відновлення на тимчасовому проєкті або сервері;
4. фіксуйте дату останньої успішної перевірки.

Відновлення перевіряє тип архіву, сумісність, контрольну суму й цільовий проєкт.
Воно може замінити файли, тому спочатку зупиніть проєкт і створіть нову резервну
копію.

## 11. Моніторинг і обмеження ресурсів

Головна сторінка моніторингу показує навантаження процесора, пам'яті, диска й
мережі VPS, а також попередження. Сторінка проєкту показує показники середовища
виконання й диска лише за наявності вимірювання. «Немає даних» означає
відсутність валідного вимірювання, а не нульове навантаження.

Власник і адміністратор можуть увімкнути обмеження:

- обмеження процесора й пам'яті застосовуються для підтримуваних середовищ
  Docker і середовищ, що запускаються безпосередньо на сервері;
- ліміти Docker Compose лише відстежуються;
- обмеження диска створює попередження, але не квоту файлової системи;
- для Minecraft потрібно щонайменше 512 MB понад налаштований JVM `Xmx`.

Перевірка працездатності має бути швидкою, не вимагати автентифікації та
підтверджувати готовність сервісу. Помилка або відповідь поза діапазонами
2xx/3xx створює одне попередження без дублікатів.

## 12. Користувачі, аудит і Telegram

Власник керує обліковими записами в **Налаштування → Користувачі**.
Адміністратор має глобальний операційний доступ. Користувачів із ролями
`maintainer` і `viewer` потрібно призначити на проєкти в параметрах проєкту.
Останнього активного власника вимкнути не можна.

Перевіряйте **Аудит** після зміни прав, перегляду секретів, відновлення, зміни
доменів і незворотних операцій. Відомості аудиту не містять паролів і секретних
значень.

Telegram необов'язковий. Власник задає токен бота й дозволений ідентифікатор
користувача Telegram у налаштуваннях, потім перезапускає сервіс бота після їх
зміни. Бот доставляє попередження й виконує підтверджені операції. Не використовуйте історію чату
як сховище секретів.

## Оновлення панелі

Оновлюйте панель до закріпленого перевіреного релізу у вікно обслуговування. До
початку створіть і перевірте резервну копію панелі та важливих проєктів поза VPS.

1. Підключіться до VPS і виберіть тег релізу, а не неперевірену рухому гілку.
2. Виконайте `sudo /opt/nectarine-panel/installer/update.sh --ref vX.Y.Z`.
3. Дочекайтеся резервного копіювання панелі, міграцій, збірки web-клієнта,
   перезапуску служб і перевірки доступності.
4. Увійдіть знову та перевірте проєкти, моніторинг, розгортання й постійні
   дані. За помилки перевірки перегляньте `systemctl status vps-panel-backend vps-panel-worker`.

Для попередньої перевірки використовуйте `--dry-run`. `--source` застосовуйте
лише для довіреної локальної копії. Не переривайте оновлення та не замінюйте
файли вручну під час роботи; за потреби відновлюйтеся з перевіреної копії.

## 13. Контрольний список для робочого середовища

Щодня або після попередження:

- перевірте проєкти з помилками, перевірки працездатності, диск і непрочитані
  сповіщення;
- дослідіть лог до багаторазових перезапусків;
- переконайтеся, що резервні копії за розкладом продовжують створюватися.

Після релізу або зміни конфігурації:

- перевірте стан і логи;
- перевірте публічну HTTPS-адресу;
- переконайтеся, що постійні дані пережили розгортання;
- швидко виконайте відкат, якщо реліз несправний.

Регулярно:

- оновлюйте NectarinePanel лише з релізу, позначеного тегом;
- змінюйте облікові дані користувачів, Git, баз даних, Telegram і застосунків;
- видаляйте невикористовувані облікові записи, призначення на проєкти, домени й копії;
- проводьте й документуйте перевірку відновлення поза основним VPS.

## 14. Поширені проблеми

| Симптом | Що перевірити |
| --- | --- |
| Git не клонує репозиторій | URL, гілку, доступ токена або ключа розгортання на читання й строк дії облікових даних. |
| Розгортання успішне, але сервіс недоступний | Лог середовища виконання, адресу прослуховування, порт проксі, оточення й шлях перевірки працездатності. |
| Файл зник після повторного розгортання | Його записано в незмінний реліз або шар контейнера, а не в `shared/`. |
| `current` не відкривається | Немає успішного релізу або ціль посилання видалена; перевірте історію. |
| Метрик немає | Проєкт ще не запускався, збирач або агент недоступний чи середовище не віддає метрику. |
| Не випускається TLS | Публічний DNS, порти 80/443, маршрут Nginx і обмеження частоти запитів. |
| Відповідь 403 | Роль або призначення на проєкт не дозволяє операцію. |
| Відповідь 502 | Серверна частина не завершила перевірену операцію агента; власник має перевірити логи панелі й агента. |

Діагностика сервера, встановлення, оновлення та відновлення описані в
[посібнику розробника](developer-guide.md). Технічні довідкові матеріали
залишаються в каталозі [`docs/`](./).
